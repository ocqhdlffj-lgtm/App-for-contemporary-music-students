# 실용음악과 입시 모집요강 통합 앱 — 설계 문서

- 작성일: 2026-09-10
- 상태: 승인됨 (1단계 설계)
- 최종 목표: 광고(AdMob)가 붙은 안드로이드 앱을 Google Play에 출시

---

## 1. 목적

실용음악과 입시생이 지원할 학교를 고를 때, 지금은 학교마다 입학처에 들어가
요강 PDF를 하나씩 받아 읽어야 한다. 학교가 100곳이 넘으므로 실제로는 아무도
전부 보지 못하고, 그 결과 **자기 조건에 맞는 학교를 놓치거나 실기고사일이
겹치는 조합에 원서를 넣는 사고**가 발생한다.

이 앱은 전국 실용음악과의 요강을 한 곳에 모아 **검색·필터·비교**할 수 있게 하고,
**실기고사일 충돌을 자동으로 경고**한다.

## 2. 범위

### 이번 단계(1단계)에서 만드는 것

- 전국 실용음악(계열) 학과 설치 대학 **전수 목록** (4년제 + 전문대)
- 학교별 구조화 데이터: 실기조건 / 전형일정(실기날짜 포함) / 반영비율 /
  모집인원 / 3년 경쟁률·입시결과 / 전공별 구분
- 모바일 우선 웹앱: 목록·필터·상세·비교·내 지원 리스트
- 실기고사일 충돌 경고
- 데이터 신뢰도 표시(`확인됨` / `부분확인` / `미확인`)

### 이번 단계에서 만들지 않는 것 (YAGNI)

로그인·회원가입, 커뮤니티·게시판, 푸시알림, 합격예측·점수계산기, 서버 백엔드,
결제. 찜·메모는 전부 기기 내 `localStorage`에만 저장한다. 서버가 없으므로
개인정보를 수집하지 않고, 개인정보처리방침이 "광고 ID 외 수집 없음"으로 단순해진다.

### 명시적 비범위

- **요강 PDF 원문을 앱에 담아 재배포하지 않는다.** 원문은 입학처 링크로 이동만 시킨다.
  (사실 정보인 일정·인원·비율은 저작권 대상이 아니므로 데이터화해도 안전하다.
  상업적 광고 수익이 붙는 앱이므로 이 경계를 지킨다.)

## 3. 단계 구성

이 프로젝트는 하나의 스펙으로 끝나지 않는다. 독립된 4개 서브프로젝트로 쪼개고,
각각 스펙 → 계획 → 구현 사이클을 돈다.

| # | 서브프로젝트 | 단계 | 상태 |
|---|---|---|---|
| 1 | 데이터 — 100+ 학교 요강 수집·구조화·갱신 | 1단계 | 이 문서 |
| 2 | 앱 UI — 검색·필터·비교·충돌체크 | 1단계 | 이 문서 |
| 3 | 안드로이드 패키징 + AdMob | 2단계 | 미착수 |
| 4 | Play 출시 — 계정·정책·테스트 | 2단계 | 미착수 |

**진행 순서 결정: 웹앱 먼저 → 앱 래핑.** 웹앱을 만들어 두면 그것이 그대로
안드로이드 앱의 내용물이 된다(Capacitor로 감쌈). 코드를 두 번 짜지 않고,
데이터가 맞는지 **링크로 먼저 검증**한 뒤 마켓에 올릴 수 있다.

## 4. 핵심 구조 결정: 앱과 데이터의 분리

화면 코드(HTML/CSS/JS)와 요강 데이터(JSON)를 완전히 분리한다.

> **이유:** 데이터를 앱에 하드코딩하면 학교 하나의 요강이 바뀔 때마다 앱을
> 새로 빌드해 **Play 재심사**를 받아야 한다. 요강은 입시철에 수시로 바뀌므로
> 이 구조로는 운영이 불가능하다. 데이터를 원격 JSON에서 받아오면 앱 업데이트
> 없이 즉시 반영된다.

**동작:**

1. 앱 실행 → 원격 JSON을 `fetch`
2. 성공 → 응답을 `localStorage`에 캐시하고 화면에 렌더
3. 실패(오프라인·서버 장애) → 캐시 사용, 없으면 앱에 동봉된 스냅샷 사용
4. 화면에 데이터 기준일(`dataVersion`) 항상 표시

**서빙 위치:** JSON을 git 저장소에 두고 GitHub Pages로 정적 서빙한다.
무료이고 이력이 git에 남아 "언제 무엇이 바뀌었는지" 추적된다.
GitHub 계정이 준비되기 전까지는 앱에 파일을 동봉해 개발하고, 2단계 착수 시 원격으로 옮긴다.

## 5. 데이터 설계

### 5.1 학교 레코드 스키마

```jsonc
{
  "id": "dongah-arts",                 // 영문 슬러그, 영구 불변
  "name": "동아방송예술대학교",
  "type": "전문대",                     // "4년제" | "전문대"
  "region": "경기",
  "deptName": "실용음악과",
  "admissionsUrl": "https://...",      // 입학처 (원문 확인 버튼 대상)
  "guideUrl": "https://...",           // 요강 PDF 링크 — 링크만, 재배포 금지

  "tracks": [{                         // 전형 단위 (수시/정시는 조건이 다름)
    "id": "susi-practical",
    "season": "수시",                   // "수시" | "정시"
    "name": "실기우수자전형",
    "majors": ["보컬", "기타", "베이스", "드럼", "건반", "작곡"],

    "quota":    { "보컬": 12, "기타": 6 },          // 전공별 모집인원
    "schedule": {
      "apply":     ["2026-09-08", "2026-09-11"],   // 원서접수 [시작, 종료]
      "practical": ["2026-10-11"],                 // 실기고사일 (복수 가능)
      "announce":  "2026-11-14"                    // 합격발표
    },
    "ratio":    { "실기": 80, "내신": 20, "수능": 0 },  // 합계 100
    "minCsat":  null,                              // 수능최저: null = 없음

    "practical": {                                 // 실기조건
      "songCount": 2,
      "songType": "자유곡",                         // "자유곡"|"지정곡"|"혼합"
      "designatedSongs": [],
      "accompaniment": "MR",                       // "MR"|"라이브"|"무반주"
      "durationMin": 5,
      "sheetMusicRequired": true,
      "notes": ""
    },

    "competition": [                               // 3년치, 공개된 것만
      { "year": 2026, "major": "보컬", "ratio": 24.5 }
    ],

    "verification": {
      "level": "확인됨",                            // "확인됨"|"부분확인"|"미확인"
      "checkedAt": "2026-09-10",
      "source": "https://..."                      // 확인에 쓴 원문 URL
    }
  }],

  "prepPoints": ["..."]                            // 해석 — 공식 요강 아님
}
```

### 5.2 `verification` — 이 설계의 안전장치

100곳을 다루면 반드시 공백이 생긴다. **빈 칸을 조용히 숨기지 않는다.**
전형(track)마다 확인 수준을 기록하고 화면에 배지로 노출한다.

- `확인됨` — 해당 연도 원문 요강에서 직접 확인
- `부분확인` — 일부 항목만 확인, 나머지 공백
- `미확인` — 학교 목록에만 있고 세부 미조사

**지어낸 값은 하나도 넣지 않는다.** 모르는 값은 `null`이고, 화면에는
"미확인"으로 표시된다. 공개하지 않는 학교의 경쟁률은 `"미공개"`로 명시한다.

### 5.3 `prepPoints` — 공식 정보와 분리

"이 학교는 무엇을 강점으로 준비해야 하는가"는 요강에 없는 **해석**이다.
데이터상 별도 필드로 두고, 화면에서 다른 색 박스 + `참고 · 공식 요강 아님`
딱지로 공식 데이터와 시각적으로 완전히 분리한다. 이것이 섞이면 앱 전체의
신뢰가 무너진다.

### 5.4 파일 구성

```
data/
  schools/          학교별 JSON 1파일 (충돌 없이 점진 추가·수정)
    dongah-arts.json
  index.json        전체 목록 + dataVersion (앱이 최초 1회 로드)
```

학교당 1파일로 나누는 이유: 100곳을 한 파일에 넣으면 수정 시 diff가 거대해지고,
여러 세션에 걸쳐 채우는 작업에서 어디까지 했는지 추적이 어렵다.

## 6. 데이터 확보 전략 — 점진적 채우기

**한 번에 끝나지 않는다.** 학교당 요강 PDF를 읽어야 하므로 여러 세션에 걸친다.
그래서 "미완성 상태에서도 쓸 수 있는" 순서로 채운다.

1. **1차 — 전수 목록**: 실용음악(계열) 학과 설치 전국 대학을 4년제/전문대로
   나눠 학교명·지역·학과명·입학처 링크까지 **전부** 확보. 모두 `미확인` 상태.
   → 이 시점에 앱은 이미 "어느 학교에 실용음악과가 있나"를 답할 수 있다.
2. **2차 — 세부 채우기**: 지원자가 많은 학교부터 실기조건·일정·비율·인원을
   채워 내려간다. 채운 학교는 `확인됨`으로 승격.
3. **3차 — 경쟁률·입시결과**: 공시된 학교만. 미공개는 명시.

출처: 각 대학 입학처, 대학알리미, 어디가(adiga).

앱에 **`세부 확인 32 / 112개교`** 형태의 진행률(숫자는 예시이며 데이터에서
자동 산출)을 상시 표시해, 미완성이라는 사실이
사용자에게 투명하게 보이도록 한다.

## 7. 화면 설계

모바일 세로 화면 기준으로 설계한다. 최종 목적지가 안드로이드 앱이므로
PC 화면부터 짜면 나중에 전부 뜯어고쳐야 한다.

### 화면 1 · 학교 목록 (홈)

학교 카드 리스트 + 상단 검색창 + 필터 칩.
카드에 표시: 학교명 / `4년제`·`전문대` 배지 / 지역 / 선택 전공의 모집인원 /
실기고사일 / `확인됨`·`미확인` 배지.

학교 카드의 배지는 학교가 가진 전형(track)들의 `verification.level` 중
**가장 낮은 값**을 쓴다(하나라도 미확인이면 학교는 `부분확인`). 낙관적으로
올려 표시하지 않는다.

**필터가 이 앱의 실질적 핵심이다:**

- 4년제 · 전문대
- 지역
- **전공** (보컬·기타·베이스·드럼·건반·작곡) — 선택 시 해당 전공을 뽑는 학교만
  남고, 인원·경쟁률도 그 전공 기준으로 바뀐다
- 수시 · 정시
- **실기 조건** — 자유곡 / 지정곡 있음 / 무반주 요구
- **수능최저 없음** (`minCsat === null`), **실기 100%** (`ratio.실기 === 100`)
  — 내신·수능이 불리한 학생이 가장 많이 찾는 조건.
  두 필터 모두 값이 `null`인(미확인) 전형은 결과에서 제외한다 —
  확인되지 않은 것을 "조건에 맞음"으로 보여주면 오지원으로 이어진다.

### 화면 2 · 학교 상세

전형별 탭(수시/정시). 입시생이 실제로 보는 순서대로 배치:
**실기조건 → 일정 → 반영비율 → 모집인원 → 경쟁률(3년)**.
하단에 `입학처 원문 확인` 버튼(외부 링크 이동).
`prepPoints`는 별도 색 박스 + `참고 · 공식 요강 아님` 딱지.

### 화면 3 · 내 지원 리스트 + 실기일정 충돌 체크

**이 앱의 핵심 차별 기능.** 찜한 학교의 실기고사일을 달력에 깔고,
**날짜가 겹치는 학교를 경고 표시**한다. 실기는 겹치면 한 곳을 반드시 버려야
하는데, 요강 PDF를 따로따로 보면 이걸 놓친다. 요강을 한군데 모았기 때문에만
가능한 기능이다.

경고 조건: 같은 날짜에 실기고사가 2개 이상. 시간까지 공개된 경우에도
**날짜 단위로 경고**한다(이동시간·대기시간을 알 수 없으므로 보수적으로).

### 화면 4 · 비교

학교 2~3곳을 나란히 놓고 실기조건·반영비율·모집인원을 표로 대조.

### 상시 노출 요소

- 하단 고정 면책: `요강은 변경될 수 있습니다. 지원 전 반드시 입학처 원문을 확인하세요.`
- 데이터 진행률 + 기준일

### 광고 자리 (2단계 대비)

하단 배너 높이 **50dp를 레이아웃에 처음부터 확보**한다. 2단계에서 AdMob을
붙일 때 화면이 밀리지 않게 하기 위함이다. 상세 화면 중간 삽입 광고는 쓰지
않는다 — 입시 정보를 읽는 흐름을 끊으면 앱을 안 쓰게 된다.

## 8. 기술 스택과 환경 제약

**현재 개발 PC에 Node.js / JDK / Android SDK / Android Studio / Python이
모두 미설치 상태다.** (2026-09-10 확인. git만 설치됨.)

따라서 1단계는 **빌드 도구가 필요 없는 구성**으로 간다:

- 순수 HTML + CSS + 바닐라 JS (ES 모듈), 빌드 단계 없음
- 프레임워크·번들러·npm 의존성 없음
- 파일을 브라우저에서 바로 열어 확인

2단계에서 Node.js + JDK + Android Studio를 설치하고 Capacitor로 감싼다.
1단계 산출물이 그대로 앱 내용물이 되므로 재작성이 없다.

**모듈 분리** (파일 하나가 커지지 않게):

```
index.html
css/style.css
js/
  data.js        데이터 로드·캐시·폴백
  schema.js      데이터 검증
  filter.js      검색·필터 로직 (순수 함수)
  conflict.js    실기일정 충돌 계산 (순수 함수)
  storage.js     찜·메모 localStorage
  ui/*.js        화면 렌더
```

`filter.js`와 `conflict.js`는 DOM을 모르는 순수 함수로 둔다. 이 둘이 앱의
로직 핵심이고, 순수하면 브라우저 없이도 테스트할 수 있다.

## 9. 법적 · 정책 요구사항

광고 수익이 붙는 상업적 앱이므로 아래는 선택이 아니다.

- **요강 PDF 재배포 금지** — 링크로만 연결 (§2 비범위)
- **면책 고지 상시 노출** — 요강 변경 가능성 + 원문 확인 유도
- **개인정보처리방침 URL** — Play 등록 필수. AdMob 사용 시 광고 ID 수집 고지 포함
- **Play Console 개발자 등록 $25 (1회)**
- **개인 개발자 계정의 클로즈드 테스트 요건** — 프로덕션 출시 전 테스터
  12명 이상 · 연속 14일. 이 정책은 계속 변경되어 왔으므로 **4단계 착수 직전에
  최신 기준을 재확인한다.**

**수익 기대치:** 실용음악과 입시생은 전국 수천 명 규모의 니치 시장이다.
광고 수익 규모보다는 실제로 쓰이는 도구를 만드는 것을 성공 기준으로 둔다.

## 10. 에러 처리

| 상황 | 동작 |
|---|---|
| 원격 JSON fetch 실패 | 캐시 → 동봉 스냅샷 순으로 폴백, 상단에 "오프라인 데이터" 배너 |
| 학교 레코드에 필수 필드 누락 | 해당 학교를 `미확인`으로 강등, 앱은 계속 동작 |
| 스키마 위반 데이터 | 콘솔 경고 + 해당 레코드 건너뜀. 앱 전체를 죽이지 않음 |
| 값이 `null` | 화면에 "미확인" 표시. 빈칸으로 두지 않음 |
| 입학처 링크 없음 | `원문 확인` 버튼 비활성 + "링크 확인 중" |

원칙: **데이터 한 건이 잘못돼도 앱 전체가 죽지 않는다.** 100곳을 점진적으로
채우는 프로젝트에서 부분적 오류는 정상 상태다.

## 11. 테스트 전략

Node가 없으므로 브라우저에서 실행되는 테스트 러너를 직접 둔다
(`tests/index.html`을 열면 결과가 표시됨). 2단계에서 Node 설치 후 Vitest로 옮긴다.

구현은 **TDD**로 진행한다 — 테스트 먼저, 그다음 구현.

**반드시 테스트할 것:**

1. **데이터 검증기 (`schema.js`)** — 이 프로젝트에서 가장 중요한 테스트.
   모든 학교 JSON에 대해:
   - 필수 필드 존재, `type`은 4년제/전문대 중 하나
   - 날짜 형식 `YYYY-MM-DD`, 접수 시작 ≤ 종료
   - `ratio` 합계가 100
   - `verification.level`이 `확인됨`인데 필수 항목이 `null`이면 **실패**
     (거짓 확신을 코드로 막는다)
2. **충돌 계산 (`conflict.js`)** — 같은 날 2개, 3개, 겹침 없음, 날짜 미상 케이스
3. **필터 (`filter.js`)** — 전공 선택 시 인원·경쟁률이 그 전공 기준으로 바뀌는지,
   조건 조합(AND) 동작
4. **폴백 (`data.js`)** — fetch 실패 시 캐시 → 스냅샷 순서

## 12. 성공 기준

1단계는 아래를 전부 만족하면 완료로 본다.

- [ ] 전국 실용음악과 설치 대학이 **누락 없이** 목록에 존재하고, 각 학교의
      입학처 링크로 실제 이동된다
- [ ] 전공 + 수능최저 없음 + 실기 100% 조건으로 필터하면 해당 학교만 남는다
- [ ] 학교 3곳을 찜해 실기고사일이 겹치면 경고가 뜬다
- [ ] `확인됨` 학교의 데이터가 원문 요강과 대조해 **틀린 값이 없다**
- [ ] 데이터 검증 테스트가 전부 통과한다
- [ ] 오프라인에서 열어도 마지막 데이터로 동작한다
- [ ] 안드로이드 화면 크기(360×640)에서 가로 스크롤 없이 읽힌다

## 13. 리스크

| 리스크 | 대응 |
|---|---|
| 요강 데이터가 틀려 학생이 잘못 지원 | `verification` 배지 + 면책 + 원문 링크. 추측값 금지 |
| 100곳 조사가 길어져 동력 상실 | 점진적 채우기 — 1차 목록만으로도 쓸 수 있게 설계 |
| 요강이 연중 변경됨 | 데이터/앱 분리로 재심사 없이 갱신 |
| 프로젝트 경로에 한글 포함(`Desktop\클로드\`) | 2단계 Gradle 빌드에서 문제가 생기면 ASCII 경로로 저장소를 이동 |
| Play 개인계정 테스트 요건 변경 | 4단계 착수 직전 최신 정책 재확인 |
| 니치 시장이라 광고 수익 미미 | 수익보다 실사용을 성공 기준으로 설정 (§9) |

## 14. 확정된 결정 기록

브레인스토밍에서 사용자가 직접 선택한 사항:

1. **데이터 범위: 전국 전수(100곳+)** — 단, 세부는 점진적으로 채운다
2. **포함 항목:** 실기조건, 전형일정, 반영비율, 실기날짜, 4년제/전문대 구분,
   전공별 정리, 모집인원, 3년 경쟁률·입시결과, 강점 준비 포인트
3. **최종 형태: 광고(AdMob) 붙은 안드로이드 앱, Google Play 출시**
4. **진행 순서: 웹앱 먼저 → 앱 래핑**
5. **데이터 채우기 방식: 점진적**
